คำศัพท์ที่ต้องรู้

      

        
UFW
firewall ของ Ubuntu ตั้ง default deny แล้วเปิดเฉพาะพอร์ตที่ต้องใช้ แพ็กเก็ตที่ไม่ตรงกฎจะถูกทิ้งเงียบ ๆ (drop) ผู้ส่งจึงเห็นแค่ timeout

        
WireGuard
VPN ระดับเครือข่าย สร้าง interface wg0 ทั้งสองฝั่ง แลกกันเฉพาะ public key ทราฟฟิกทุกชนิดที่ route เข้า wg0 จะถูกเข้ารหัสส่งผ่าน UDP

        
NAT (masquerade)
S2 เปลี่ยนที่อยู่ต้นทางของแพ็กเก็ตจาก 10.8.0.2 เป็น IP ของ S2 เอง ก่อนส่งต่อไป S1 ทำให้ S1 ไม่ต้องรู้จักวง 10.8.0.0/24 และไม่ต้องแก้ route

        
ip_forward
ตัวเปิดให้ Linux ส่งต่อแพ็กเก็ตระหว่าง interface ถ้าปิด S2 จะรับแพ็กเก็ตจาก wg0 แล้วไม่ส่งต่อไป S1

        
SSH SOCKS (ssh -D)
เปิด proxy ที่ 127.0.0.1:1080 บน Client โปรแกรมที่ตั้งให้ใช้ proxy (เช่น curl --socks5-hostname) จะส่งคำขอผ่านการเชื่อมต่อ SSH ไปที่ S2 แล้ว S2 เป็นฝ่ายต่อไป S1

        
handshake
การจับมือเข้ารหัสระหว่างสอง peer ของ WireGuard ถ้า wg show ไม่มีเวลา handshake ล่าสุด แปลว่าอุโมงค์ยังไม่ติด

1
สร้าง user และ key (ทำก่อนล็อก SSH)

      
ตอนล็อก SSH เราจะปิดรหัสผ่านและอนุญาตเฉพาะ peter ถ้ายังไม่มี user นี้และ key ก่อนล็อก จะเข้าเครื่องไม่ได้อีก จึงต้องสร้างและทดสอบก่อนเสมอ

      
      
      

        
ต้องเห็น
ครั้งแรกที่ต่อ ssh จะถามยืนยัน fingerprint ให้พิมพ์ yes ส่วน ssh-copy-id จะขอรหัสของ peter เป็นครั้งสุดท้าย หลังจากนั้น ssh peter@<S1_IP> ต้องเข้าได้โดยไม่ถามรหัส

        
พลาดบ่อย
ถ้าเคยสร้าง key แล้ว ssh-keygen จะถามว่าจะเขียนทับไหม ให้ตอบ n แล้วใช้ key เดิม และห้ามข้ามขั้น ssh peter@... เพราะต้องรู้ว่า key ใช้ได้จริงก่อนไปขั้นล็อก

      

    


    
    

      
2
ล็อก SSH (S1 และ S2)

      
เป้าหมายคือเข้าเครื่องได้ด้วย key ของ peter เท่านั้น ใครเดารหัสผ่านหรือลองเข้าเป็น root จะถูกปฏิเสธตั้งแต่ด่านแรก

      
      
      

        
ต้องเห็น
sshd -T แสดง passwordauthentication no, kbdinteractiveauthentication no, pubkeyauthentication yes, permitrootlogin no, allowusers peter

        
พลาดบ่อย
ตั้งชื่อไฟล์ขึ้นต้น 00- เพื่อให้ชนะ 50-cloud-init.conf ที่อาจเปิด password ไว้ และ AllowUsers peter ทำให้ admin เข้าผ่าน SSH ไม่ได้อีก จึงต้องเปิด session เดิมค้างไว้ตอนทดสอบ โดน reset VM หัก 2 คะแนน

      

    


    
    

      
3
S1: Caddy

      
S1 เป็นเว็บที่ต้องปกป้อง หน้าเว็บมีเลขกลุ่ม ชื่อสมาชิก และ TOKEN ซึ่งเป็นหลักฐานว่าเราเข้าถึง S1 ได้จริง

      
      

        
ต้องเห็น
ss แสดงว่า caddy ฟังที่ :80 และ curl -s http://127.0.0.1/ ที่ S1 ต้องเห็นหน้ามี TOKEN (ทดสอบในเครื่องก่อนเปิด UFW ได้)

        
พลาดบ่อย
ห้าม chmod 777 ดู log ด้วย sudo journalctl -u caddy -f ข้อความ "Caddyfile input is not formatted" เป็นแค่คำเตือนเรื่องการจัดบรรทัด ไม่กระทบการทำงาน

      

    


    
    

      
4
S2: WireGuard

      
ใช้วิธี NAT (ง่ายสุด S1 ไม่ต้องแก้ route) แต่ละฝั่งสร้าง key คู่ของตัวเอง แล้วส่งให้อีกฝั่งเฉพาะ public key ห้ามโชว์หรือคัดลอก private key ข้ามเครื่อง

      
      
      

        
ต้องเห็น
sudo wg show มี interface wg0 พร้อม listening port ตรงกับ <WG_PORT>, ip link show wg0 เจอ interface และ sudo iptables -t nat -S POSTROUTING มีกฎ MASQUERADE ของ 10.8.0.0/24 ไป <S1_IP>

        
พลาดบ่อย
ใช้ <<EOF แบบไม่มีเครื่องหมายคำพูด เพื่อให้ shell แทนค่า $SERVER_KEY, $CLIENT_PUB, $IFACE ให้เอง (ไม่ต้องก๊อปคีย์ด้วยมือ) และใส่ > /dev/null เพื่อไม่ให้ tee พิมพ์ private key ขึ้นจอ ห้ามใช้พอร์ต 51820 ถ้าอาจารย์ไม่ระบุ

      

    


    
    

      
5
UFW (ตั้ง 22 ก่อน enable เสมอ)

      
UFW เปลี่ยนสองเครื่องให้ปฏิเสธทุกอย่างที่ไม่อนุญาต S1 เปิดพอร์ต 80 ให้ S2 เท่านั้น ส่วน S2 เปิด SSH, พอร์ต WireGuard และอนุญาตส่งต่อทราฟฟิกจาก wg0 ไป S1:80

      
      
      

        
ต้องเห็น
Status: active และ Default: deny (incoming), allow (outgoing) ที่ S1 ต้องมี 22/tcp ALLOW IN Anywhere กับ 80/tcp ALLOW IN <S2_IP> ที่ S2 ต้องมี <WG_PORT>/udp และบรรทัด route ที่หน้าตาแบบ <S1_IP> 80/tcp on <IFACE> ALLOW FWD Anywhere on wg0

        
พลาดบ่อย
ufw enable จะถามว่าอาจตัด SSH เดิมไหม ให้ตอบ y (ปลอดภัยเพราะอนุญาต 22 ไว้แล้ว) และห้ามมีกฎ 80 ALLOW Anywhere ที่ S1 (C3 และ C4 ได้ 0 ทันที)

      

      
หมายเหตุกฎ 10.8.0.0/24 ที่ S1: จากการทดสอบ ทราฟฟิกผ่าน WireGuard ถูก NAT ที่ S2 ก่อนถึง S1 ทำให้ Caddy เห็นต้นทางเป็น <S2_IP> เสมอ กฎ <S2_IP> จึงเป็นกฎที่ทำงานจริง ส่วนกฎ 10.8.0.0/24 จะมีผลก็ต่อเมื่อไม่ทำ NAT เปิดทิ้งไว้ไม่เสียหาย แต่ไม่จำเป็น

    


    
    

      
6
Client config

      
ฝั่ง Client บอก WireGuard ว่าจะคุยกับ S2 ที่ไหน และให้ส่งอะไรเข้าอุโมงค์ ค่า AllowedIPs ระบุเฉพาะวง 10.8.0.0/24 กับ <S1_IP>/32 ทราฟฟิกอื่นของเครื่องจึงไม่ผ่านอุโมงค์

      
      

        
ต้องเห็น
sudo ls -l /etc/wireguard/wg0.conf แสดงสิทธิ์ -rw------- (600)

        
พลาดบ่อย
ไฟล์นี้มี private key ของ Client ถ้าลืม chmod 600 ไฟล์จะเป็น 644 และทุก user บนเครื่องอ่านคีย์ได้ (ฉบับเดิมไม่มีบรรทัดนี้) ส่วน public key ของ S2 สั้น จะคัดลอกด้วยมือจาก sudo cat /etc/wireguard/server.pub แทน scp ก็ได้

      

    


    
    

      
7
ทดสอบ (Category E)

      
ต้องพิสูจน์สามอย่าง: เข้าเว็บได้ผ่าน WireGuard, เข้าเว็บได้ผ่าน SSH SOCKS และเข้าตรงไม่ได้ จากนั้นดู log ว่า S1 เห็นแต่ S2

      
      
      
      

        
ต้องเห็น
Path A: wg show มีบรรทัด latest handshake, ping ตอบ และ curl เห็น TOKEN  Path B: ip link show wg0 แจ้งว่าไม่มี device และ curl ผ่าน SOCKS เห็น TOKEN  Negative: curl รอ 5 วินาทีแล้วคืน 28 และ nc แจ้ง open แค่พอร์ต 22

        
log ที่ถูกต้อง
ใน log ของ Caddy (JSON) ทั้ง path A และ path B มี "remote_ip":"<S2_IP>" และต้องไม่มี IP ของ Client เลย เพราะคำขอตรงจาก Client ถูก UFW ทิ้งก่อนถึง Caddy

        
พลาดบ่อย
ลืมปิด WG ก่อนทดสอบ path B จะทำให้ไม่รู้ว่าใช้ทางไหน และ negative test ต้องทำตอน WG ปิดเท่านั้น ถ้า ping ไม่มีในเครื่อง ให้ติดตั้ง iputils-ping

      

    


    

      
สิ่งที่ต้องระวัง

      
ห้ามทำ: ปิด UFW, เปิดพอร์ตเกินจำเป็น, ก๊อป private key ข้ามเครื่อง, ใช้พอร์ต 51820 (ถ้าอาจารย์ไม่ระบุ)

      
แบ่งงานแนะนำ: M1 รับ S1 (Caddy และ UFW), M2 รับ S2 (WireGuard และ UFW), M3 รับ Client (key, WG, SOCKS), M4 รับ SSH hardening ทั้งสองเครื่อง แล้ว cross-review กัน

    


    

      
เตรียมตอบรายบุคคล

      
ทุกคนต้องอธิบายได้ กดที่คำถามเพื่อดูคำตอบ

      
ทำไมต้อง allow 22 ก่อน enable
UFW ตั้ง default deny incoming พอ enable ปุ๊บ ทุกอย่างที่ไม่มีกฎจะถูกทิ้ง ถ้ายังไม่ได้ allow 22 session SSH ที่ใช้อยู่จะค้างและเข้าเครื่องไม่ได้อีก

      
ถ้า ip_forward ปิดจะเกิดอะไร
S2 รับแพ็กเก็ตจาก wg0 ได้ ทำให้ ping 10.8.0.1 ยังตอบ แต่ไม่ส่งต่อไป S1 curl ไป S1 จึงค้างจน timeout

      
ทำไม S1 ต้อง allow ทั้ง 10.8.0.0/24 และ S2_IP
จากการทดสอบกับวิธี NAT S1 เห็นต้นทางเป็น S2_IP เท่านั้น กฎ S2_IP จึงเป็นกฎที่ใช้จริง กฎ 10.8.0.0/24 จำเป็นเฉพาะกรณีไม่ทำ NAT ซึ่ง S1 ต้องรู้ route กลับไปวง 10.8.0.0/24 ด้วย

      
AllowedIPs = 0.0.0.0/0 ต่างอย่างไร
ที่ Client AllowedIPs คือทั้งรายการ route ที่ส่งเข้าอุโมงค์ และตัวกรองแพ็กเก็ตขาเข้า ค่าเฉพาะอย่าง 10.8.0.0/24, <S1_IP>/32 ส่งเข้าอุโมงค์เฉพาะสองปลายทางนั้น (split tunnel) ส่วน 0.0.0.0/0 ส่งทราฟฟิกทั้งเครื่องผ่าน S2 (full tunnel) ซึ่งต้องมี NAT ออกอินเทอร์เน็ตและเสี่ยงตัด SSH ของตัวเอง ฝั่ง S2 ใช้ 10.8.0.2/32 เพื่อรับจาก peer นี้เฉพาะที่อยู่นี้

      
ssh -D ต่างจาก VPN อย่างไร
ssh -D เปิด SOCKS proxy ระดับโปรแกรม ใช้ได้กับโปรแกรมที่ตั้งให้ใช้ proxy และรองรับเฉพาะ TCP ไม่มี interface หรือ route ใหม่ ส่วน WireGuard เป็น VPN ระดับเครือข่าย มี wg0 และ route ทุกโปรแกรมใช้ได้โดยไม่ต้องตั้งค่า รวม UDP และ ping

      
--socks5-hostname ต่างจาก --socks5 อย่างไร
--socks5 ให้ curl แปลงชื่อโฮสต์เองบน Client แล้วส่ง IP ให้ proxy ส่วน --socks5-hostname ส่งชื่อให้ proxy (S2) เป็นฝ่ายแปลง ถ้าใช้ IP ตรง ๆ อย่าง http://<S1_IP>/ สองแบบให้ผลเหมือนกัน

    


    

      
ซ้อมด้วย VM (VirtualBox / VMware) - ตรงกับข้อสอบจริง 100%

      
การสอบจริงใช้ Linux 3 เครื่องในวง LAN เดียวกัน ดังนั้นวิธีซ้อมที่ดีที่สุดและไม่มีปัญหากวนใจคือการติดตั้ง Ubuntu Server บน VirtualBox หรือ VMware แล้วตั้งโหมด Bridged Adapter


      
ใช้ ISO เดียวกันทั้ง 3 เครื่อง: ดาวน์โหลด Ubuntu Server 22.04 หรือ 24.04 LTS ไฟล์เดียว สามารถใช้สร้าง VM ทั้ง S1, S2 และ Client ได้ทั้งหมด


      
1. การตั้งค่าสร้าง VM ทั้ง 3 เครื่องใน VirtualBox

      

        

          
เครื่องชื่อใน VMRAM / Diskโหมด Network (สำคัญ)หน้าที่ตามโจทย์

          
            
Server 1S11-2 GB / 20 GBBridged Adapter (เลือกการ์ด Wi-Fi/LAN เครื่องจริง)Web Server (Caddy พอร์ต 80) + SSH

            
Server 2S21-2 GB / 20 GBBridged Adapter (เลือกการ์ด Wi-Fi/LAN เครื่องจริง)WireGuard VPN (wg0) + SSH Jump

            
ClientClient1 GB / 20 GBBridged Adapter (เลือกการ์ด Wi-Fi/LAN เครื่องจริง)เครื่องผู้ใช้ทดสอบเข้าเว็บทุกเส้นทาง

          
        

      


      
ขั้นตอนการสร้าง VM ใน VirtualBox:

      
    
        
  1. กดปุ่ม New (รูปดาวสีฟ้า) → ตั้งชื่อเครื่อง (S1, S2, หรือ Client) → เลือกไฟล์ Ubuntu Server ISO
    2. 
        
  2. ตรงขั้นตอนสร้าง user ให้ตั้งชื่อผู้ใช้เริ่มต้นเป็น admin (ตามที่โจทย์ระบุว่าบัญชีเริ่มต้นคือ admin ที่มีสิทธิ์ sudo)
    3. 
        
  3. ตั้งค่า Network ให้ต่อวง LAN จริง: คลิกขวาที่ VM → Settings → Network → เปลี่ยนจาก NAT เป็น Bridged Adapter และเลือกการ์ดเครือข่ายที่ใช้ออกเน็ต
    4. 
        
  4. ข้อแนะนำเรื่อง Wi-Fi: หากต่อ Wi-Fi หอพักหรือมหาวิทยาลัยมักมีระบบ AP Isolation บล็อกการคุยกัน ให้ต่อสาย LAN หรือเปิด Hotspot มือถือ ให้ทุกเครื่องมาเกาะวงเดียวกัน
    5. 
      


      
2. คำสั่งติดตั้งแพ็กเกจสำหรับแต่ละเครื่อง (ตรงตามแล็บ p.md)

      
เมื่อเปิด VM แต่ละเครื่องขึ้นมาและล็อกอินด้วย admin แล้ว ให้คัดลอกคำสั่งของเครื่องนั้นไปวางใน Terminal ได้ทันที:


      
      
หมายเหตุ S1: ถ้า apt install caddy ไม่เจอ ให้เปิด universe repo ก่อนด้วย sudo add-apt-repository universe -y && sudo apt update && sudo apt install -y caddy


      

      

      
3. ตรวจสอบการเชื่อมต่อก่อนเริ่มทำโจทย์

      
ขั้นที่ 1: ดูเลข IP ของแต่ละเครื่อง พิมพ์คำสั่งนี้ในทุกเครื่อง:

      
      
จดเลข IP ที่ได้มา (เช่น 192.168.43.x) โดยนำไปใช้แทนค่า <S1_IP> และ <S2_IP> ในโจทย์


      
ขั้นที่ 2: ทดสอบว่า Client คุยกับ S1 และ S2 ได้ ที่เครื่อง Client ให้ลอง ping:

      

      
ขั้นที่ 3: หาชื่อ Interface ของ S2 สำหรับใช้ทำ WireGuard NAT Masquerade (มักเป็น enp0s3 ใน VirtualBox หรือ ens33 ใน VMware):

      

      

        ทำไมไม่แนะนำให้ใช้ WSL2 สำหรับการซ้อมข้ามเครื่องคอมพิวเตอร์?
        

          
    
            
  • โหมด Mirrored: มักเจอปัญหา Error: 0x8007054f (Failed to configure network, falling back to networkingMode None) บนไดรเวอร์ Wi-Fi หลายยี่ห้อ ทำให้ไม่มี IP และตัดเน็ตทิ้งทั้งหมด
    • 
            
  • โหมด NAT: แม้จะใช้ netsh interface portproxy ส่งต่อพอร์ตได้ แต่ Windows รองรับเฉพาะ TCP เท่านั้น ในขณะที่ WireGuard (หมวด D) ต้องใช้ UDP ทำให้ Client ไม่สามารถเชื่อมต่อ VPN ข้ามเครื่องได้
    • 
            
  • การใช้ VirtualBox แบบ Bridged Adapter จึงเป็นวิธีที่เหมือนข้อสอบจริง 100% และไม่มีปัญหาจุกจิกเรื่องเน็ตเวิร์ก
    • 
          

        

      

    


    
    

      
ล้างค่าเพื่อเริ่มซ้อมใหม่ (Clean Reset & ปลดล็อก SSH)

      
เมื่อซ้อมเสร็จ 1 รอบ หรือทำผิดพลาดแล้วต้องการเคลียร์การตั้งค่าทั้งหมดให้กลับสู่จุดเริ่มต้น เพื่อฝึกซ้ำตั้งแต่ Step 1 ถึง 7 โดยไม่ต้องติดตั้ง Ubuntu ใหม่


      

        
⚠️ ทำไมรีเซ็ต/รีบูต VM แล้ว SSH เข้าด้วย ubuntu หรือ admin ไม่ได้? (Permission denied)

        
เพราะใน Step 2 เราได้เปิดใช้ SSH Hardening: AllowUsers peter และ PasswordAuthentication no ไว้ใน /etc/ssh/sshd_config.d/ ทำให้ระบบปฏิเสธ user อื่นทั้งหมด และไม่รับรหัสผ่านผ่าน SSH

      


      
วิธีแก้ด่วน: ปลดล็อก SSH ให้กลับมาเข้าได้ตามปกติ

      
หากถูกล็อก ไม่ต้องตกใจ! ให้ไปที่หน้าต่าง Console ของ VM โดยตรง (หน้าจอดำใน VirtualBox/VMware ที่ไม่ใช่ผ่าน SSH) ล็อกอินด้วยบัญชีเริ่มต้น (ubuntu หรือ admin) แล้วรันคำสั่งบรรทัดนี้:

      
      
เมื่อรันเสร็จ SSH จะกลับมารองรับ password authentication และอนุญาตให้ทุก user ล็อกอินจากเครื่องจริงภายนอกได้ทันที

    8. 
        
  8. ยังไม่ได้ทดสอบ: คำสั่งติดตั้ง Caddy จาก repo ทางการ และการตั้ง WSL แบบ mirrored (ระบุไว้ในหน้าแล้ว)
